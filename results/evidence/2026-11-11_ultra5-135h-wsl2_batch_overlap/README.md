# Batch I/O overlap: parallel decode + async write

Host: Intel Core Ultra 5 135H laptop, WSL2, 18 logical CPUs (see `doctor.json`).
Build: `main` at the commit that added `--decode-threads` / `--async-write`, cpu preset (Release).

Each run is one cold `framepipe batch` invocation on `cpu-omp` with 4 threads,
edges, writing real PNGs. `runs/<scenario>_dec<N>_win<W>_<write>_r<round>.json`
is the unmodified `batch_report.json`. The four configurations were interleaved
over three rounds. `summary.csv` is recomputed from those reports.

- `hd`: 40 frames, 1920×1080 → 1280×720 (`manifests/hd_seq.jsonl`)
- `uhd`: 12 frames, 3840×2160 → 1920×1080 (`manifests/uhd_seq.jsonl`)

Manifest paths point at `data/bench/`, generated by
`python3 scripts/generate_fixtures.py benchmark --out data/bench`.

| Scenario | 1 decoder, sync write (old behaviour) | 2 decoders, async | 4 decoders, window 4, sync | 4 decoders, window 4, async |
|---|---:|---:|---:|---:|
| HD fps (median of 3) | 19.7 | 38.1 | 58.8 | **71.0** (3.6×) |
| 4K fps (median of 3) | 4.7 | 9.5 | 14.4 | **16.2** (3.4×) |

Why: decoding a 1080p PNG takes ~35 ms and a 4K PNG ~145 ms on this host,
while processing takes ~2–5 ms. One decoder caps the batch at ~1/decode_time.
Parallel decoders lift that cap. The writer thread then hides PNG encode
(~8–10 ms per HD output). The reorder window must be at least as large as the
decoder count, otherwise decoders idle waiting for a free slot (measured: 4
decoders with a window of 2 gave ~35 fps).

Outputs are byte-identical to the serial path
(`Batch.ParallelDecodeMatchesSerialByteForByte` and `cli_integration`).
