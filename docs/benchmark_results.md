# Benchmark results

**Scope of these results:** CPU only. No GPU result exists. The CUDA
backend has not been executed (see implementation_status.md). Nothing below
supports a GPU speedup claim.

## Hardware and build

| | |
|---|---|
| CPU | Intel Core Ultra 5 135H (hybrid P/E cores), 18 logical CPUs (9 cores × 2 threads as reported by `lscpu` inside the VM) |
| Host | WSL2, kernel 6.18.54.1-microsoft-standard-WSL2, Ubuntu 24.04.3 LTS, laptop, power state not controlled, cpufreq not exposed |
| GPU | none visible (no NVIDIA driver in WSL) |
| Compiler | GCC 13.3.0, Release `-O3 -DNDEBUG`, ISO C++17 (no FMA contraction), no fast-math |
| Libraries | OpenCV 4.10.0 (minimal source build), OpenMP 4.5 (libgomp) |
| Git revision | null — repository had no commits when measured (`run.json.git_note`) |

## CPU core processing (`cpu_core_wall_ms`, repeat workload, pooled median of 1000 samples)

| Scenario | Input → output | cpu-ref (scalar) | cpu-omp (12 thr) | opencv-cpu (1 thr) | omp / ref speedup |
|---|---|---:|---:|---:|---:|
| tiny | 64×64 → 64×64 | 0.064 | 0.031 | 0.033 | 2.1× |
| small | 640×480 → 320×240 | 1.45 | 0.29 | 0.79 | 5.0× |
| hd | 1920×1080 → 1280×720 | 15.3 | 4.77 | 8.34 | 3.2× |
| uhd | 3840×2160 → 1920×1080 | 43.0 | 13.4 | 25.1 | 3.2× |
| odd | 1919×1079 → 1279×719 | 14.3 | 2.90 | 7.51 | 4.9× |
| upscale | 640×480 → 1280×960 | 15.9 | 3.88 | 6.69 | 4.1× |
| same | 1920×1080 → 1920×1080 | 28.9 | 9.95 | 12.5 | 2.9× |

All times are milliseconds. The ring workload (4 different frames) lands
within roughly ±20% of these numbers (`*_ring` directories). Run-to-run
variation on this laptop VM is large. For example, cpu-ref on `hd` (15.3 ms)
and on the identical `hd_radius3` configuration (19.3 ms), measured about an
hour apart, differ by 26%. Treat differences under ~30% between separate
runs as noise. Comparisons inside one run (backends interleaved by rotation)
are more reliable than comparisons between runs.

## Application and batch

`application_wall_ms` (read, decode, process, quantize, PNG encode/write) for
HD was 62 ms (cpu-ref), 63 ms (cpu-omp), and 58 ms (opencv-cpu). Core
processing is 5–15 ms of that. **Decode and PNG encode dominate the
application path.** At the HD scale, 3× faster processing changes
end-to-end time by about 0–10%. The same pattern holds at every size from
small up. A GPU backend would face this same I/O bound, which is
the spec's "faster kernels but slower app" risk, now measured for the CPU
side. Batch throughput (completed frames / batch wall s): HD 12.8–14.4 fps,
UHD 4.5–5.1 fps, small ~125 fps, all I/O-bound.

|---|---:|---:|---:|
| radius 1 | 15.9 | 3.5 | 9.3 |
| radius 3 | 19.3 | 5.0 | 9.1 |
| radius 7 | 34.8 | 8.7 | 10.7 |

| stage resize | 4.7 | 0.69 | 4.6 |
| stage blur | 13.8 | 3.0 | 5.7 |
| stage edges | 18.5 | 4.4 | 9.7 |

The scalar Gaussian scales linearly with radius. OpenCV's separable filter is
nearly flat and beats 12-thread cpu-omp at r = 15 on a single thread. This
points to vectorization rather than threading as the missing CPU
optimization. The profile agrees: the two Gaussian passes are 58% of scalar
self-time at r = 3 (`cpu_ref_profile.txt`: vertical 30.2%, horizontal 27.7%,
grayscale 16.2%, Sobel 13.3%, resize 7.5%).

## M5 optimization log: cpu-omp scheduling

1. **Observed bottleneck.** In the thread sweep, cpu-omp HD time fell from
   13.6 ms (1 thread) to 2.9–3.5 ms (12–14 threads), then rose to 15.9 ms at
   16 threads and 41 ms at 18 threads (p95 99 ms). The first implementation
   used one static contiguous chunk per thread with a barrier after every
   stage.
2. **Hypothesis and change.** On hybrid P/E cores in a shared VM, one slow or
   descheduled thread holds every stage barrier. Change: 4 × threads chunks
   with `schedule(dynamic, 1)`. Each row is still computed by one thread with
   the same code (bit-identical to cpu-ref, tested). The static variant stays
   available via `-DFRAMEPIPE_OMP_STATIC_SCHEDULE=ON`. Its implementation
   string is `schedule=static`, and the default is `schedule=dynamic4x`.
3. **Correctness evidence.** Unit tests (`CpuParallel.MatchesReferenceExactly`)
   and the oracle suite pass for both variants.
4. **Measured before/after.** Median / p95 ms, HD edges, 3 × 100 samples per
   cell, two sessions:

   | threads | static s1 | dynamic s1 | static s2 | dynamic s2 |
   |---:|---|---|---|---|
   | 4 | 6.93 / 9.88 | 7.74 / 10.36 | 6.70 / 10.64 | 6.73 / 8.35 |
   | 8 | 6.07 / 7.99 | 6.06 / 7.89 | 5.80 / 6.47 | 5.39 / 6.41 |
   | 12 | 4.22 / 4.88 | 4.54 / 5.29 | 5.12 / 11.40 | 4.57 / 5.05 |
   | 16 | 4.99 / 40.5 | 8.86 / 35.1 | 4.01 / 30.6 | 3.49 / 27.5 |
   | 18 | 46.9 / 91.7 | 37.9 / 85.8 | 28.2 / 65.4 | 25.7 / 67.4 |

5. **Outcome and tradeoff.** Inconclusive. Medians differ by less than the
   session-to-session variation. Dynamic scheduling slightly reduces the
   p95 tail at 16–18 threads in both sessions, but it does not remove the
   cliff. The hypothesis "load imbalance from static chunks" is therefore
   not supported. The remaining explanation, oversubscription of the
   VM's virtual CPUs (the cliff starts as threads approach the logical-CPU
   count while the OS, WSL, and the host share them), was not isolated, because the
   host offers no CPU pinning or frequency control. Decision: keep dynamic4x as default
   (equal medians, no worse tail, more robust to uneven cores), keep the
   static variant for comparison, and run the matrix at 12 threads. The
   larger measured opportunity is SIMD in the Gaussian passes (see radius
   table), which is not yet implemented.
